Report: MediaPipe / Pose Estimation Optimizations in GaitKeeper
1) High-level architecture (how they get smoother motion)
GaitKeeper’s “smoothness” comes from stacking multiple, different kinds of smoothing
depending on the purpose:
1. Model/runtime choice for stability
o Prefer BlazePose via MediaPipe runtime (more stable than TFJS runtime),
and set TFJS backend explicitly.
2. Per-frame pose smoothing for jitter (visual / general)
o A simple exponential moving average (EMA) on each keypoint’s x/y, gated
by keypoint confidence.
3. Kalman filtering for ankle tracking (analysis-grade stability + velocity)
o A lightweight 2D Kalman filter that smooths ankle position and estimates
velocity (vx, vy), enabling more stable footstrike logic.
4. Signal smoothing for metrics (cadence / strike detection robustness)
o Moving average over ankle position time series + robust outlier handling
(median + MAD).
These layers are deliberately not the same: what looks smooth and what is analytically
stable are handled separately.
2) MediaPipe / BlazePose configuration and runtime choices (pose-estimation.ts)
TFJS backend choice
They explicitly force:
• tf.setBackend('webgl')
With a comment that WebGPU may not be available. This is a practical stability/perf
choice for browsers.
Preferred pose model
They try BlazePose first:
• poseDetection.SupportedModels.BlazePose
• runtime: 'mediapipe'
• solutionPath: 'https://cdn.jsdelivr.net/npm/@mediapipe/pose'
• modelType: 'lite'
Why this matters:
• MediaPipe runtime often behaves more consistently than TFJS runtime in-browser.
• modelType: 'lite' usually means faster inference (less accurate than heavy/full, but
often “stable enough” and less laggy).
Fallback model
If BlazePose fails to load, they fall back to MoveNet:
• poseDetection.SupportedModels.MoveNet
• modelType: poseDetection.movenet.modelType.SINGLEPOSE_THUNDER
Why this matters:
• THUNDER is typically slower but more accurate/stable than LIGHTNING.
Inference call
They run detection as:
• detector.estimatePoses(video)
No explicit options are passed here (so they’re relying on defaults for flipping,
maxPoses, etc.).
3) Skeleton smoothing for video playback / rendering (pose-estimation.ts)
Temporal smoothing (EMA)
They maintain a short history:
• Pose history length cap: 5 frames
(poseHistory.push(currentPose), then shift if > 5)
But the smoothing itself uses only the most recent previous pose, not all 5 frames.
EMA parameters:
• EMA alpha: 0.5
Comment: “0 = all history, 1 = no smoothing” (in practice they’re doing a 2-frame
EMA).
Confidence gating:
• If keypoint has no score or score < 0.3, they do no smoothing for that keypoint and
return it as-is.
So the effective rule is:
• Only smooth if kp.score >= 0.3 AND previous keypoint exists
• x_smooth = 0.5*x_now + 0.5*x_prev
• y_smooth = 0.5*y_now + 0.5*y_prev
Rendering thresholds and visualization “smoothness”
They also “smooth” the appearance by refusing to draw questionable points:
• Do not draw segments unless both endpoints have score ≥ 0.3
• Do not draw joints unless score ≥ 0.3
• Joint radius: 6 px (larger points look steadier)
Strike arrow animation (visual clarity)
Their strike marker fade is time-based:
• Fade duration (maxAge): 300 ms
• Alpha: 1 - age/maxAge
This doesn’t smooth the skeleton, but it makes overlays feel fluid and readable.
4) Kalman filtering (the “serious smoothing”) (kalman-filter.ts)
This file is a simple 2D Kalman filter with state:
• [x, y, vx, vy]
Default noise parameters
Constructor defaults:
• processNoise (Q): 0.1
• measurementNoise (R): 5.0
• initial covariance diagonal P: [10, 10, 10, 10] (high initial uncertainty)
Time-step handling
• dt = min((currentTime - lastTime)/1000, 0.1)
dt capped at 0.1s (100ms) to prevent giant jumps if frames stall.
Velocity update blending
When they have a valid dt:
• they estimate velocity from innovation: innovation / dt
• then blend it into state velocity with:
o velocity blend alpha: 0.3
(How much to trust new velocity measurement)
They also only do this if:
• dt > 0.001 seconds
Landing / toe-off detection thresholds (uses filtered y, vy)
These are not “smoothing” parameters, but they matter for how stable detection appears.
Landing (detectLanding) defaults:
• near ground threshold: 20 px
• moving down: vy > 5 px/s
• not too fast: vy < 200 px/s
Toe-off (detectToeOff) defaults:
• threshold: 15 px
• toe-off if:
o vy < -5 px/s (moving up) OR
o y < groundY - threshold (above ground)

Foot strike type classification tuning values
In determineFootStrikeType():
• If frames < 10: returns default confidence 0.3
• They use a lower threshold to include more frames:
o minConfidence: 0.2 (explicitly lower than 0.3)
They compute a combined confidence from multiple keypoints:
• confidence = min(leftAnkle.score, leftToe.score, leftHeel.score OR 0.5,
leftKnee.score, leftHip.score)
Important: heel/toe are treated more leniently
• If heel score missing they use 0.5 as fallback (“more lenient with heel/toe
detection”)
They choose “analysis frames” as:
• minima of footStrike distance, else
• frames with confidence > 0.5
Then:
• avgConfidence = clamp(totalConfidence/analysisFrames.length, min=0.5, max=0.9)
Classification thresholds (degrees):
• forefoot if avgFootAngle > 5
• heel if avgFootAngle < -3
• else midfoot
Foot strike position estimation (robust stats)
Key tuning constants:
• minConfidence: 0.3
• Use up to 30 frames to estimate pixels-per-meter from nose→ankle height.
• minFramesBetweenStrikes: round((fps/30) * 5)
(At 30fps → 5 frames; at 60fps → 10 frames)
They filter “reasonable” strike positions by meters:
• only keep if positionMeters is between:
o -0.5 m and 2.0 m
They use only the most recent strikes:
• keep 5 most recent positions
Outlier removal:
• robust center: median
• deviation: MAD (mean absolute deviation in their code)
• reject outliers beyond:
o 2 × MAD
Confidence scoring uses:
• consistency = max(0, 1 - stdDev/0.3) (so 0.3 is the “acceptable spread” scale)
• sample count confidence: min(1, filteredPositions.length / 3)
• outlier ratio: filteredPositions.length / recentPositions.length
Weights:
• 0.5 consistency
• 0.3 sample count
• 0.2 outlier ratio
Final clamp:
• clamp position to [-1, 3] foot lengths
• display uses absolute value and rounds to 1 decimal place

7) Practical “how to apply this to your pipeline”
If your problem is “my MediaPipe skeleton jitters across a video,” GaitKeeper suggests a
very pragmatic progression:
Level 1 (easy, big win): confidence-gated EMA per joint
• Use their exact thresholds to start:
o score >= 0.3
o EMA alpha = 0.5
• Improve it slightly over theirs by keeping a persistent smoothed value per joint
(instead of only referencing last pose once).
Level 2: Kalman filter on high-noise joints
• Start with ankles/wrists/toes using:
o Q = 0.1, R = 5.0, velocity blend alpha = 0.3
• Skip updates when confidence drops; just predict.
Level 3 (often the “secret sauce”): render interpolation
Your uploaded files don’t show explicit 60-FPS interpolation, but if your detector runs at
~15–30 FPS, interpolating between pose frames at render time can make the skeleton
look dramatically smoother even with the same keypoint quality.
